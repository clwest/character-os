## What Didn't (and Why)

### Context-kit `init` dumped its own source into the repo

- **Attempted:** `context-kit init "character-os" --target . --force --quiet`.
- **Surprise:** alongside the expected anchor docs + skill,
  `context-kit init` copied its own implementation
  (`context_kit.py` 35KB + `cli/` package) into the new repo's
  root. This is a self-bootstrapping pattern but it doubles the
  surface area of the new repo with code that already exists at
  the globally-installed binary.
- **Fix:** removed `context_kit.py` and `cli/` after init; kept
  the anchor docs and the skill. The globally installed
  `context-kit` binary at `/Users/donkeyking/.local/bin/context-kit`
  serves any commands the project needs.
- **For next time:** consider proposing a `--no-vendor` flag to
  context-kit init, or use `context-kit adopt` (which doesn't
  vendor source) on an existing scaffolded repo. Not blocking.

### The design doc's subtree command needed correction

- **Attempted:** the design doc §6.7.5 step 3 said
  `git subtree add --prefix=media-engine runway-hackathon main`
  directly.
- **Why it didn't work:** that would import the *entire*
  runway-hackathon repo (backend + frontend + docs + scripts) into
  `media-engine/`. We only want backend/.
- **Actual fix:** ran `git subtree split --prefix=backend -b
  backend-history` in runway-hackathon first, then subtree-added
  that history-only branch into character-os.
- **Doc consequence:** design doc §6.7.5 step 3 has a small bug in
  the literal command. Worth a follow-up edit to the design doc
  in SESSION 107 — keep the intent (preserve history via subtree)
  but record the actual two-step `split` → `add` pattern.

### Real Phase 1 work — not started

- **Why not in this session:** scope. Phase 1 per design doc §7
  covers User/Workspace/Membership models, Google OAuth +
  email/password, Stripe + tier middleware, admin scaffold,
  Spokesperson + Video stubs, internal API for Django↔FastAPI.
  All of that is its own work and the operator wanted a clean
  handoff point after the scaffold itself.
- **Resume in SESSION 107.** Recommended first slice: data model
  (User extension / Workspace / Membership / Spokesperson stub /
  Video stub) before auth or billing — get the schema correct
  before adding flows on top.

## AI Notes

This session ran as a tight loop: design doc → repo scaffold →
context-kit install → subtree import → docs/scripts carryover →
Django scaffold → smoke gates. The operator approved a 4-item
checklist (path / name / phase order / push timing) and we executed
end-to-end without re-checks.

One judgment call worth flagging: I chose to remove the vendored
`context_kit.py` + `cli/` that context-kit init dropped into the
new repo root. Globally installed binary already covers everything
those files do; vendoring them at the project root would have been
visual noise in every directory listing for no benefit. Operator
didn't ask about this explicitly — flagging here so it's part of
the trust calibration log if they would have preferred the vendor.

The 89-commit FastAPI history landed cleanly via `git subtree
add`. Every PR FA-FI commit message is now reachable in the new
repo's `git log`. That's a non-trivial preservation — if we'd
copied the directory instead, the institutional memory of why each
service module exists would have been irrecoverable from this
repo.

For SESSION 107, the most leverage-y next move is the **core data
model** (User/Workspace/Membership/Spokesperson/Video). Get the
schema right with no auth, no billing, no media calls — pure
models + migrations + admin registration. Once the data model is
solid, auth and billing slot on top cleanly. Going in the other
order (auth first) tends to create rework when the model needs to
change.
